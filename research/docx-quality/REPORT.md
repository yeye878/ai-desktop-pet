## 一、结论先行

**问题是链路里缺一个「文档编译器」，不是模型写不出内容。**

桌面上的《AI领域新闻报告汇总_2026年11月.docx》内容质量其实达标：全文 64 个 body 级段落，其中 48 个正文段落里有 34 段使用了加粗字段名，标题层级正确（6 个二级、5 个三级，没有越级），3 张表格、A/B/C/D 可信度分级、口径风险提示都在。但它解包后只有 **3 个 OOXML 部件**，`document.xml` 里 **命名样式 0 个、大纲级别 0 个、真实编号 0 个、超链接 0 个**，并且根元素连 `xmlns:r` 命名空间都没声明——这意味着它**在物理上没有能力**挂页眉、页码、目录、超链接。这不是模型偷懒，而是三层架构问题叠加的结果：

1. **排版责任错配**：工具描述向模型承诺「Markdown 会自动转换成排版好的 Word」，于是模型把版式决策外包给渲染器；而渲染器是约 120 行手写解析逻辑，被外包的版式直接蒸发。
2. **表达通道被压到最低公共分母**：契约只有 `path / title / content` 三个字段，Markdown 解码器又只认 7 种结构，模型能想到的文档元素大多数在契约里无字段可写。
3. **生成不可见、不可迭代**：工具只返回「已生成 N 字节」，没有结构、没有页数、没有校验；模型既看不见成品，也无法自我纠正。

结论性判断：**内容质量已经够用，缺的是「文档工程」的承担者**。补上语义层（样式、大纲、域、分节、关系）之后，同一份内容可以直接达到专业报告水准——本次研究用一份参考实现做了实测验证（见第七节）。

## 二、现状诊断：差在哪，差多少

### 2.1 包结构：3 个部件 vs 14 个

| 部件 | 桌面产物 | Word 正常文档 | 后果 |
| --- | --- | --- | --- |
| `word/document.xml` | 有 | 有 | 正文 |
| `word/styles.xml` | 缺 | 有 | 无命名样式、无标题层级 |
| `word/numbering.xml` | 缺 | 有 | 列表是手写符号，不自动编号 |
| `word/settings.xml` | 缺 | 有 | 域不自动更新、无中文排版选项 |
| `word/header1.xml`、`footer1.xml` | 缺 | 有 | 无页眉、无页码 |
| `word/_rels/document.xml.rels` | 缺 | 有 | 无法引用页眉、超链接、图片 |
| `docProps/core.xml`、`app.xml` | 缺 | 有 | 文件属性标题/作者/日期全空 |
| `[Content_Types].xml` | 仅 1 条 Override | 全量登记 | 只能容纳 3 部件极简包 |

### 2.2 语义指标：三项核心计数全部为 0

| 指标 | 计数 | Word 中的实际表现 |
| --- | --- | --- |
| `w:pStyle` 命名样式引用 | 0 | 样式面板全是「正文」；改版要逐段改 |
| `w:outlineLvl` 大纲级别 | 0 | 导航窗格空白；引用→目录插入后找不到目录项 |
| `w:numPr` 真实编号 | 0 | 增删条目编号不重排；无法多级编号 |
| `w:hyperlink` 超链接 | 0 | 来源不可点击 |
| `w:sectPr` 分节 | 1（仅 body 末尾） | 无法「封面单独一节、页码从正文起算」 |
| `w:br` 软换行 | 0 | 多行字段被合并成一段 |

### 2.3 肉眼可见的排版缺陷（附实证）

- **软换行被合并**：解析器把连续多行用空格拼成一段。产物第 3 段正是「覆盖周期 / 成稿时间 / 信息性质 / 一句话结论」四项被挤成 **264 字一个段落**，本应是四个字段四行。
- **`---` 变字面量**：倒数第二段的正文就是三个减号（`paras[121]` 的 `<w:t>---</w:t>`），分隔线成了正文垃圾。
- **表格列宽均分**：`col_w = 内容宽 / 列数`，5 列表格里「时间」这类短列与「关键要求」这类长句列等宽，中文被迫频繁换行；三张表的 `gridCol` 之和分别为 9,024 / 9,025 / 9,024，与 `tblW` 的 9,026 也不一致（整数除法丢余数）。
- **无页码、无封面、无目录**：多页报告翻页靠数，文档没有「报告」的骨架。
- **`rPr` 顺序违规 72/223（32%）**：`w:b` 被排在 `w:sz` 之后（69 处）、`w:color` 被排在 `w:sz` 之后（3 处），严格校验的消费方会丢弃这些格式。
- **表格单元格不解析行内格式**：表格里写 `**重点**` 会原样输出星号（与正文行为不一致）。

### 2.4 内容层其实达标的部分

- 正文 4,784 字符（其中中文 3,276 字）；48 个正文字号段落平均 75 字、中位 63 字，超过 150 字的有 5 段（最长 264 字，即被合并的四个字段）；
- 34 个正文段落含加粗 run，说明模型主动使用了 `**字段名：**` 写法；
- 标题层级没有越级，3 张表格结构完整；
- 正文里没有 `**`、`](`、`|` 泄漏——**模型写出的 Markdown 是干净的**。

一句话：**模型交付了合格的「稿」，渲染器把它排成了「草稿」。**

## 三、根因：为什么直连 API 特别容易生成这种文档

### 3.1 责任错配：模型把排版外包给了一个不存在的排版系统

工具描述（`tools.rs:989`）明确写着「正文用 Markdown 语法书写，会自动转换为排版好的 Word 文档」；系统提示（`lib.rs:2226-2249`）又强化了一次。对模型而言这是理性决策：排版交给渲染器，自己只管内容。但真实渲染器 `build_docx_bytes`（`tools.rs:1464-1499`）只打包 3 个部件，`markdown_to_document_xml`（`tools.rs:1835-1956`）只有 122 行解析逻辑。**被外包出去的排版责任，落在了一个没有样式系统的实现上。**

对比 DSH / Claude Code 路径：模型自己就是排版作者——可以写 OOXML、可以用 `python-docx`、可以调校验技能、可以渲染检查。不存在「责任交接」这一跳，也就不存在「交接蒸发」。

### 3.2 通道窄：能表达的元素，契约里没有字段

契约三个字段装不下：作者、日期、副标题、要不要封面、要不要目录、页码从哪页起、表格列宽意图、来源链接、图片。模型只能把它们压缩进一段 Markdown；而 Markdown 只有 7 种结构（标题、段落、列表、表格、引用、代码、分隔线），OOXML 却有样式、域、关系、节、编号等一整套语义对象。**两者之间存在语义断层，而中间只有一个 122 行的解码器。**

更具体地说，解码器有 5 处硬性保真损失：软换行合并（`tools.rs:1849`）、`---` 未处理（解析循环无该分支）、假列表（`tools.rs:1654` 手写「• 」前缀）、表格均分列宽（`tools.rs:1724`）、无链接/无样式/无分节。

### 3.3 闭环断：模型在「盲写」，且看不见上一版

一次生成 = 一条 assistant 消息里塞进整篇正文，工具返回 `Word 文档已生成: 路径（N 字节）`，回合结束。模型拿不到任何结构反馈：不知道 `---` 成了字面量、不知道字段被合并、不知道表格挤成了竖条。数据库只存 `content / thinking`、不存工具调用（`db.rs:103-123`），所以用户说「再改改」时，模型连上一版写过什么都不知道；提示词（`lib.rs:2237`）教的唯一改法是「整篇重新生成覆盖」。

### 3.4 两个放大器

- **提示词没有文档方法论**：Word 相关提示词（`lib.rs:2226-2249`）只有参数说明，没有「先提纲后写作」「字段独立成段」「表格 ≤5 列」「来源要可点击」；反而与基础人设冲突——`client.rs` 的 `BASE_SYSTEM_PROMPT` 要求「默认回复简短自然，通常 2-3 句话即可」。
- **没有输出预算概念**：三处请求体构造都不含 `max_tokens`（`api_client.rs:1014-1037、1120-1141、1193-1214`），长文能否一次吐完取决于模型默认上限；一旦参数被截断，`agent.rs:839-862` 的处理是整轮重试或放弃，而不是续写。

### 3.5 三条路径的能力对比

| 维度 | 直连 API（现状） | DSH + office 技能 |
| --- | --- | --- |
| 工具面 | 40 条固定 JSON Schema | 技能即工作流：生成、校验、渲染 |
| 表达通道 | Markdown 子集 → 3 部件极简包 | 任意脚本/库，可产出完整 OOXML 包 |
| 验证能力 | 无（仅 roundtrip 断言文本存在） | `validate` + 渲染截图，能看到真实版面 |
| 迭代方式 | 整篇重新生成 | 局部改 XML / 局部重排 / 反复比对 |
| 规划 | 无计划工具 | 任务清单 + 多步执行 |

**差的不是模型，是「文档工程」在链路里没有承担者。**

## 四、目标态：四级质量阶梯

| 级别 | 名称 | 验收断言 |
| --- | --- | --- |
| L0 | 能打开 | Word 打开无「发现不可读取的内容」提示 |
| L1 | 有语义 | `styles.xml` 存在；标题全部带 `outlineLvl`；导航窗格可见 |
| L2 | 有骨架 | 封面节 + 正文节；页脚 `PAGE`/`NUMPAGES` 域出值；目录域可更新 |
| L3 | 有细节 | 表格按内容分配列宽 + 不跨页断行 + 表头重复；超链接可点；水平线正确；文档属性齐全 |
| L4 | 有一致性 | 样式驱动改版（改一处全篇生效）；中英文混排正确；长文分段写入并可自检 |

现状定位：**L0**（能打开），加上一部分 L3 的「视觉属性」（字号、边框、底纹）。**L1/L2 完全缺失**——这也解释了观感差距：做得像，但「文档系统」没建起来。

## 五、提升方案

### 5.1 P0：补语义层（预估 M，1–2 天）

1. **先决条件**：`w:document` 根元素补 `xmlns:r` 命名空间声明。不补这一条，任何 `r:id`（页眉页脚引用、超链接、图片）都会造成未绑定前缀，Word 打开必弹修复提示。
2. 新增 `word/styles.xml`：`docDefaults` + `Title/Subtitle/Heading1-3/BodyText/Quote/CodeBlock/TableHeader/Caption/ListParagraph`；`document.xml` 全部改用 `w:pStyle`，字号行距下沉到样式里（不再每个 run 硬编码）。
3. 标题样式内嵌 `outlineLvl`（0/1/2）+ `keepNext`/`keepLines` → 导航与目录立即可用。
4. 新增 `word/settings.xml`：`updateFields=true`、`compat`、中文版式选项（`kinsoku`/`overflowPunct` 属于段落属性，放 `styles.xml` 的 `BodyText`，不是 settings）。
5. 新增 `word/header1.xml` + `word/footer1.xml`，页脚 `PAGE`/`NUMPAGES` 域（「第 X 页 / 共 Y 页」），页眉文档名；`sectPr` 补 `headerReference`/`footerReference`。
6. 分节：封面节（首页不同 `titlePg`）+ 正文节（`pgNumType start=1`）；封面承载标题/副标题/作者/日期。
7. 目录域 `TOC \o "1-3" \h \z \u` + 目录样式（`TOC1-3`）。
8. 补齐 `word/_rels/document.xml.rels`、`docProps/core.xml`、`app.xml`，并同步 `[Content_Types].xml` 的 Override。
9. 语义修复：`---` → 段落 `pBdr` 下框线；软换行不再 `join(" ")`，改为 `w:br` 或按行分段；`rPr` 子元素按 schema 顺序输出（`rFonts→b→bCs→i→iCs→color→sz→szCs`）。

### 5.2 P1：补内容元素（预估 S–M，半天）

10. 表格列宽按内容分配：中文宽字符计 2 单位，列宽 = 自然宽 × 单位宽 + 内边距，再归一到 A4 内容宽 9026 twips 并钳制；每格写 `tcW`，并保证 `sum(gridCol) == tblW`。
11. 行级控制：`cantSplit`（行不跨页）、`tblHeader`（表头重复，现有实现已正确）、斑马纹、单元格垂直居中。
12. 表格单元格接入行内解析（`**粗体**` 在表格里也要生效），分隔行判定要排除「只有短横线的数据行」。
13. `word/numbering.xml` + `w:numPr`：真编号、多级缩进。
14. 超链接：`w:hyperlink` + `r:id` + 外部关系（`TargetMode="External"`）。
15. 正文 `firstLineChars=200` 首行缩进 2 字符、行距 1.5、两端对齐、`w:lang` 与 `w:noProof`（避免代码串被拼写检查标红）。

### 5.3 P2：补长文档能力与闭环（预估 M，2–3 天）

16. **契约 v2**：`mode: create|append|finalize` + `markdown`/`blocks` 双通道 + `frontmatter`（title/subtitle/author/date/org）+ `options`（cover/toc/pageNumbers/header/headingNumbering）。不传新字段即走 v1 通道，向后兼容。
17. **返回值升级**：从「N 字节」改为「结构摘要 + warnings」——段落数、标题层级、表格数、链接数、是否含目录/页码/封面、超长段落告警。这是零成本的「校验回合」。
18. **独立 `inspect_docx` 工具**：13 条静态探针（部件齐全、样式引用、大纲覆盖、编号、链接关系、页脚域、分节、目录、表格几何、字面量残留、超长段落、文档属性、字体缩进），供中间态复查与旧文档体检。
19. 内置 2–3 套模板（商务报告/新闻简报/技术白皮书）：模板管样式，代码管内容。
20. 图片、脚注、书签 + `REF` 交叉引用。

### 5.4 针对「新闻汇总」场景的模板化建议

- **固定骨架**：摘要卡 → 主线表 → 分板块 → 风险 → 时间线 → 来源分级；
- **固定块**：每节统一「事件 / 为什么重要 / 观察清单 / 说明」，渲染器可直接套样式；
- **可信度可视化**：高/中高/中 → 单元格底纹绿/黄/灰；
- **来源可点击 + 文末分级表**，把「待核验」做成显式标记而不是口吻。

## 六、工程路线对比

| 路线 | 做法 | 成本 | 质量上限 | 风险 |
| --- | --- | --- | --- | --- |
| A 手写 OOXML 补全 | 扩展现有 `build_docx_bytes` 为 14 部件模板 | M | 高（可控到每一个 XML 属性） | 兼容性细节多，需 golden test |
| B 引入 Rust docx 库 | 用成熟库生成 | M | 中高（受库特性覆盖限制） | 新依赖、特性缺口、升级维护 |
| C 模板注入 | 预置 .docx 模板，运行时替换正文 | M | 很高（样式由 Word 定义） | 模板维护、跨平台字体 |

**推荐 A + C**：P0/P1 用手写补全（已有基础，零新依赖，二进制不膨胀），P2 引入模板机制把「样式设计」交还给真实 Word 模板。B 路线在需要复杂图表/域时再评估。

## 七、效果验证：同一份内容的前后对比

用同一份内容（64 段正文、3 张表）做了一份「目标质量」的参考实现，实测对照如下：

| 指标 | 现状产物 | 参考实现 |
| --- | --- | --- |
| OOXML 部件数 | 3 | 14 |
| 命名样式引用 `pStyle` | 0 | 129 |
| 大纲级别 `outlineLvl` | 0 | 20（标题 1–3 级 = 0/1/2） |
| 真实编号 `numPr` | 0 | 32（3 张表外全部为真列表） |
| 超链接（外部关系） | 0 | 4 |
| 页码 | 无 | `PAGE` / `NUMPAGES` 域 |
| 目录 | 无 | `TOC` 域（1–3 级） |
| 封面 | 无 | 独立封面节 + 首页不同 |
| 文档属性 | 无 | title / author 已写入 |
| 水平线 | 字面量 `---` | 分隔线样式 ×2，无字面量残留 |
| 表格 | 列宽均分、无行级控制 | `tcW` ×59、`cantSplit` ×15、表头重复 ×3 |
| 正文排版 | 12pt、1.3 倍行距、无缩进 | 样式驱动：首行缩进 2 字符、1.5 倍行距、两端对齐 |

参考实现由一份「手写 OOXML + zip」的 Python 脚本产出（刻意不用现成库，以便逻辑可 1:1 移植回 Rust），生成后被 `python-docx` 正常打开，`lxml` 校验全部部件良构，`docProps/app.xml` 记录 6 页。它证明：**同一份内容、同一套解析习惯，只要把语义层补齐，观感差距就是「草稿 → 报告」。**

## 八、度量：把「文档质量」变成一个可计算的分数

建议在工具返回值里内置一个 **DQ（Document Quality）分**，由 12 项布尔断言加权组成，0–100：

| 断言 | 分值 |
| --- | --- |
| 必需部件齐全（styles/numbering/settings/header/footer/rels/docProps） | 20 |
| 标题全部带 `outlineLvl` 且层级连续 | 15 |
| 页脚含 `PAGE`/`NUMPAGES` 域 | 10 |
| 存在 `TOC` 域且 `updateFields` 开启 | 10 |
| 列表使用 `numPr` 真编号（无手写「• 」残留） | 10 |
| 超链接有外部关系且可点击 | 10 |
| 表格按内容分配列宽 + `cantSplit` + 表头重复 | 10 |
| 正文首行缩进 + 1.5 倍行距 + 中文字体 | 5 |
| `docProps` 中 title/author/created 非空 | 5 |
| 无字面量残留（`---`、`**`、`](`、`|`） | 3 |
| 超长段落（>200 字）≤ 1 | 1 |
| `rPr`/`pPr` 子元素顺序符合 schema | 1 |

这份分数可以直接作为 `create_docx` 返回的 `stats.dq`，也可以作为回归测试基线。按此口径，**现状产物几乎为 0 分**（12 项断言里只有中文字体一项部分满足）；本次参考实现为满分（`rPr` 顺序违规 0/64）。分数的意义在于把「文档好不好」从主观观感变成可比较、可回归的工程指标。

## 九、落地顺序

1. **第一周（收益最高）**：P0 的 1/2/3/4/5/6/8/9——把文档从 L0 拉到 L2。其中「根元素补 `xmlns:r`」「样式系统」「页脚页码」三项是其余一切的前置。
2. **第二周**：P1 全部 + P2 的契约 v2 与结构化诊断，达到 L3，并让模型能在同一回合内自我修正。
3. **第三周**：模板机制 + 渲染验收 + DQ 分，达到 L4，把「生成 → 诊断 → 修复」变成自动收敛的闭环。

## 十、边界与风险

- **兼容性优先**：手工拼 OOXML 最大的风险是「少一个 part、少一条 Override、关系悬空、`r:id` 未声明命名空间」，任一都会触发 Word 修复提示。必须建立 golden test：生成后用 Word 打开并断言无修复提示，同时断言「必然弹窗」的写法清单为零。
- **域更新是正常的**：`TOC`/`PAGE` 依赖 Word 打开时更新域，`updateFields` 会提示「是否更新」，这是专业文档的常规行为，但要在回复里告知用户。
- **字体跨平台**：`w:eastAsia="微软雅黑"` 在 Windows 可用；若桌宠后续跨平台，需要字体回退链与 `w:cs` 字体。
- **维护成本**：一旦样式集中到 `styles.xml`，后续改版只改一处；手写 OOXML 的长期成本可控，但每次新增部件都要同步 `[Content_Types].xml` 与关系文件，建议用「部件表驱动」的方式管理。
- **不要重写解析层之前先改视觉**：顺序应该是「部件 → 样式 → 结构 → 元素 → 视觉」，反过来做会不断返工。
